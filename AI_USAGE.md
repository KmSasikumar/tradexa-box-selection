## Prompts / tasks given (summarised faithfully)

The agent was given one task, in full, by the coordinating agent:

> Build the Tradexa Django hiring assignment end-to-end and push it to
> GitHub. Spec: an ecommerce platform where the warehouse needs to know
> which shipping box to use for an order. Products have dimensions and
> weight; boxes have internal dimensions, maximum weight capacity and
> cost. Build a small Django-based system that recommends the most
> suitable box for an order. Fit rules: (a) total order weight <= box
> max_weight, (b) every product's dimensions fit inside the box's
> internal dimensions allowing rotation (compare sorted dimensions),
> (c) total product volume <= box internal volume. Among fitting boxes
> recommend the cheapest; if none fits, return an explicit "no suitable
> box" result, never a forced fit. Reject the naive volume-only approach
> in the design notes. REST API: CRUD for products and boxes, create
> orders with items, a recommendation endpoint. SQLite, requirements.txt,
> CI workflow running the tests. Tests: fits exactly, too heavy
> rejected, too large in one dimension rejected, rotation allowed,
> cheapest among fitting boxes chosen, no-box case returns null + reason,
> empty order handled. Docs: README, AI_USAGE, CHAT_TRANSCRIPT (a truthful
> build-session log, not a fake human chat), LEARNINGS, TEST_OUTPUT
> (verbatim), TEST_CASES. Push to a public GitHub repo named
> tradexa-box-selection under KmSasikumar. Do NOT email Tradexa or
> submit anything; do not invent data, test results or transcripts.

No further human prompts were given during the build; every decision
below was made by the agent inside that task and then verified by
running the code.

  viewsets, the `POST /api/orders/{id}/recommend/` action, the admin

  passed (see `TEST_OUTPUT.md`).
- The documentation files — accepted as written, with every claim
  checked against what was actually built and run.

## Output rejected or modified

- **Volume-only fit logic — rejected.** An early design sketch (fit =
  total volume <= box volume) was rejected before any code was written,
  because it would accept a 100 cm item in a 20 cm box. The final
  algorithm requires all three rules: weight, per-product sorted
  dimensions, and volume.
- **A leftover helper — removed.** A first draft of `services.py`
  contained an unused `Decimal` import and a placeholder guard function
  with no purpose. Both were removed during a cleanup edit before the
  tests were run; the final file contains only the algorithm.
- **README example — corrected.** A first draft of the README showed
  abbreviated box objects inside `evaluated_boxes`. That did not match
  the real API response (which serializes the full box), so the example
  was corrected to show the full fields.
- **No AI-generated code was accepted blindly.** Every file was run:
  `manage.py check`, the full test suite, and a live API smoke test
  (see "Verification steps").

## AI mistakes found during the build

One real mistake, found by running the code rather than by review:

- **Smoke test failure — `ALLOWED_HOSTS`.** The first API smoke test
  (run through `manage.py shell` with DRF's `APIClient`) failed with
  `DisallowedHost: Invalid HTTP_HOST header: 'testserver'`, because the
  generated settings had `ALLOWED_HOSTS = []`. The Django test runner
  allows `testserver` automatically, which is why the test suite passed
  while the shell smoke test failed. Fix: `ALLOWED_HOSTS` now lists
  `localhost`, `127.0.0.1` and `testserver`, with a comment explaining
  why `testserver` is there. After the fix the smoke test passed and
  the test suite was re-run (still 12/12 passing). This is recorded
  here because it is exactly the kind of environment difference a
  reviewer would want to know about: tests passing does not prove the
  shell/API path works, so both were run.

No other AI mistakes were found: the test suite passed on its first
run, and the smoke-test recommendation (cheapest fitting box, with the
too-small box rejected) matched the hand-computed expectation.
